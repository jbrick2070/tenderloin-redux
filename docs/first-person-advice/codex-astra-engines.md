I interpret “no download” as **no installation**, and “single-digit MB” as the **total cold HTTP transfer**, including the engine and required game assets. No engine can guarantee 3D or WebXR in literally every browser; the existing 2D edition remains valuable as a fallback.

**My recommendation is to qualify Godot first, because it preserves the most working game—but keep it only if it passes the download, phone-performance and accessibility requirements. If you need one engine selected immediately under the absolute single-digit-MB constraint, three.js is the strongest fit.**

That distinction is consequential. Godot is the cheapest place to implement first-person, but the current build cannot honestly be presented as meeting all your hard constraints.

The source supports the following port-cost assessment:

- **Staying preserves substantial implementation.** I counted **16,327 lines in `main.gd` plus 7,815 across 26 other top-level GDScript files**. The project uses Compatibility rendering and already disables web threading. Godot 4.7.2 is pinned in CI. These counts describe scope; they are not a calendar estimate. [Project settings](C:/tenderloin-redux/godot/project.godot:7), [export settings](C:/tenderloin-redux/godot/export_presets.cfg:11), [CI version](C:/tenderloin-redux/.github/workflows/deploy-pages.yml:29)
- **First-person is an integration project.** The current camera is orthographic, and `update_camera()` positions it around a target. Walking uses custom clearance checks and small movement substeps on flat `y=0` ground; it is not a general gravity/slopes controller. Characters are visually enlarged by **2.15×**, and corridor travel can reach **24 m/s**. Camera height, perceived scale, movement speed, labels, cutaways and interaction placement need a street-level review. [Camera creation](C:/tenderloin-redux/godot/main.gd:2058), [walking](C:/tenderloin-redux/godot/main.gd:8295), [camera update](C:/tenderloin-redux/godot/main.gd:15098), [scale/speed constants](C:/tenderloin-redux/godot/main.gd:10)
- **The geography transfers well; its presentation does not transfer automatically.** The 188 buildings, metric coordinates, polygon rings, triangulation, heights, trees and lidar records are portable JSON. Godot’s `SurfaceTool` mesh construction, shaders, collision nodes, procedural details and UI wiring must be replaced in another engine. Measured footprints and heights also do not establish fully surveyed façades, entrances or street-level terrain. [Building data](C:/tenderloin-redux/godot/data/buildings.json), [mesh construction](C:/tenderloin-redux/godot/main.gd:1667)
- **A JavaScript migration has a real reuse advantage.** `browser-next/` already contains separated activity rules, conversations, chapter logic, saves and accessibility UI. Some modules explicitly identify themselves as ports of Godot activities. A three.js/Babylon/PlayCanvas frontend can import these modules rather than translate all gameplay again. Coverage differences, coordinate conversion and activity lifecycle still need review. Rust, Lua and C# migrations lose most of that direct reuse. **The browser requirements should drive the implementation whichever engine wins.**

1. **Static hosting and broad device reach.** Keep a WebGL2 path and feature-detect optional WebGPU. Godot’s existing single-thread configuration is appropriate for ordinary static hosting. Phone support still requires real Safari/iOS and Chrome/Android performance checks; desktop success is insufficient. Unity now documents mobile-browser support too, so rejecting it on an old “desktop only” claim would be inaccurate. [Godot web support](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html), [Unity browser compatibility](https://docs.unity.com/en-us/engine/6000.0/manual/platform-specific/webgl/intro/browsercompatibility)

2. **First-person input and comfort.** Use an explicit click to enter Pointer Lock, release it for menus and Escape, provide keyboard turning, and implement separate touch movement/look regions. Include a usable alternative to mouse capture. Preserve guided walking or overview navigation, allow sensitivity adjustment, avoid mandatory head bob and camera shake, and honor reduced-motion preferences. Pointer Lock requires a user gesture; touch controls are a separate design task. [Pointer Lock documentation](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_Lock_API)

3. **Screen-reader UI.** Favor semantic HTML for dialogue, choices, settings, objectives and edition switching. JavaScript engines integrate with this directly; Godot, Unity, Bevy and Defold need deliberate browser bridges. The present Godot bridge creates live announcements and a textual status summary, which does **not** prove complete accessible interaction. Godot reduced-motion handling was not verified. The browser edition already has semantic controls and a reduced-motion preference, making it useful reusable work. [Godot accessibility bridge](C:/tenderloin-redux/godot/main.gd:11456), [browser HTML](C:/tenderloin-redux/browser-next/index.html:24), [motion preference](C:/tenderloin-redux/browser-next/game.js:57)

4. **Shared saves.** Every viable browser option can use `tenderloin-redux.godot.save.v1`. Preserve the **same origin**, schema, validation, optional fields, write budget and sequencing—not just the key name. The existing [JavaScript save adapter](C:/tenderloin-redux/browser-next/godot-save.js:1) is particularly valuable. Engine defaults such as filesystem-backed saves or Unity `PlayerPrefs` are not automatic substitutes for this contract. `localStorage` is origin-scoped, so moving one edition to another hosting domain would separate its storage. [Storage documentation](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage)

5. **Later WebXR.** Godot, three.js, Babylon and PlayCanvas all provide credible paths. VR still requires headset-specific input, locomotion, UI and performance work; a first-person camera does not complete it. Keep XR optional and detect support over HTTPS. WebXR remains unavailable in some widely used browsers, regardless of engine. [WebXR availability](https://developer.mozilla.org/en-US/docs/Web/API/WebXR_Device_API)

For one-person maintenance, Godot minimizes immediate reimplementation. A JavaScript frontend offers a different long-term benefit: **the 2D and 3D editions could share one gameplay/save/UI layer**, reducing parallel implementations. Three.js makes sense for this relatively constrained procedural neighborhood, but it leaves more controller and interaction code in your care. Babylon becomes more attractive as integrated collision, XR and scene features grow in importance.

**I would recommend switching under these conditions:**

- **Godot fails a bounded qualification effort.** If a reproducible release cannot deliver the required playable content under **10,000,000 transferred bytes**, keep the separate PCK limit and move the first-person frontend to **three.js**. Count the engine, scripts, fonts and required assets; caching does not excuse the first visit. If the cap means *uncompressed* size, the current Godot export already fails decisively.
- **Browser accessibility or mobile behavior remains costly to bridge.** If the semantic HTML UI and existing browser rules become the natural center of the game, using a JavaScript 3D renderer alongside them is a stronger architecture than continuing two gameplay implementations.
- **WebXR becomes a committed primary mode.** Evaluate **Babylon.js** against three.js using the actual target headset and required interactions. Choose Babylon if its integrated features remove enough application code while still meeting the measured download budget. Possible future VR alone is not a reason to leave Godot.
- **The distribution requirements change substantially.** Unity becomes more reasonable with existing C# expertise, required middleware or broader native-platform plans. Unreal, O3DE and Stride deserve reconsideration only after static-browser delivery stops being mandatory.

No alternative Tenderloin build was produced or benchmarked in this review. Live compressed transfer, real-phone performance, complete screen-reader operation and headset behavior remain **unverified**.
